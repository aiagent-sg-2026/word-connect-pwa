# Word Connect PWA — V1.3 Gameplay Roadmap

Baseline: V1.2 production commit `900d57fa58cdd6e3af8e8ff0af6e97d00d7a0c69`.

## Goal

V1.3 should improve replay/retention without making the core gameplay screen busier or weakening the offline-first architecture. The primary mechanic is an offline deterministic Daily Challenge built from the existing immutable production campaign. V1.3 does not generate or mutate production words at runtime.

## Product principles

- Keep normal gameplay unchanged and single-viewport at 320x568.
- Daily Challenge is optional; it must never block campaign progression.
- Reuse the verified `campaign-en-v2` levels. Do not create a second runtime dictionary/generator path.
- Preserve V1.2 saves, achievements, stats, economy history, hints, and update lifecycle.
- Avoid fake scarcity, timers, energy systems, ads, or punitive streak loss.
- Offline state is authoritative for V1.3. No account/cloud dependency.

## Phase 1 — Daily Challenge foundation

### Daily identity

Create a stable `YYYY-MM-DD` local-calendar day key. Select the daily puzzle deterministically from the immutable campaign using a versioned function of:

`dailyPolicyVersion + campaignVersion + dayKey -> levelId`

The same device/day/campaign must always resolve to the same level. Selection must not modify the level contract or its hash.

### Durable state

Add a dedicated daily record keyed by `[profileId, dayKey]` containing at minimum:

- `dayKey`
- `campaignVersion`
- `levelId`
- `levelHash`
- `startedAt`
- `completedAt?`
- `rewardClaimed`
- daily target/bonus result snapshot needed for recovery

Do not overload ordinary campaign `ProgressRecord` identity. Daily play can reuse gameplay logic, but its durable identity must remain distinct from campaign progression.

### Entry UX

Add one compact `Daily` entry from the existing non-gameplay surface (Settings/Stats area or a small header affordance only if it still passes the viewport contract). Do not add another permanent gameplay row.

Daily screen should communicate:

- Today's challenge
- Completed / not completed
- Daily streak summary
- Reward state

## Phase 2 — Daily streak and reward

### Streak

Track consecutive completed local-calendar days. A missed day ends the streak; it does not remove earned achievements or coins. No countdown pressure is required.

Derive streak from durable completion records where practical instead of maintaining an independently drifting counter.

### Reward

Use a versioned daily reward policy. Reward must be granted exactly once per day and written atomically with completion/reward state and the economy event.

Initial design target: modest reward relative to the V1.2 economy; daily play should be useful but must not recreate the pre-V1.2 coin inflation problem. Final value must be chosen from simulation before implementation.

Clock manipulation is not treated as a security problem in the offline-only V1.3 product. The architecture must remain deterministic and internally consistent, but it must not pretend to provide server-grade anti-cheat without a server clock.

## Phase 3 — Daily stats and milestones

Extend Player Stats with compact daily metrics:

- Daily challenges completed
- Current daily streak
- Best daily streak

Add only a small number of evidence-based milestones, for example first Daily completion and a multi-day streak. Achievement unlock remains idempotent and export/import safe.

## Phase 4 — Save/migration/recovery

V1.3 must define a new save-data migration only if the durable schema requires it. Requirements:

- V1.2 save imports without loss.
- Daily records export/import with strict validation.
- Imported daily records must reference known immutable campaign levels/hashes.
- Duplicate daily rewards must fail closed or reconcile without double credit.
- Existing economy events are never rewritten.
- Reset continues to clear all local player state.

## Phase 5 — Acceptance gates

Required before release:

1. Existing V1.2 unit/build/content/reviewer/offline gates remain green.
2. `campaign-en-v2`, production corpus, and Golden evidence remain byte-for-byte unchanged.
3. Deterministic daily selection tests cover dates, campaign version, and policy version.
4. Daily completion/reward is idempotent and atomic; reload cannot duplicate reward.
5. V1.2 save -> V1.3 migration and V1.3 export/import round-trip pass.
6. Chromium and WebKit pass Daily entry/play/completion/reload flows.
7. 320x568, 360x640, 393x659, 390x844 remain zero vertical/horizontal scroll during core gameplay with >=44px interactive targets.
8. Warm offline reload and installed-PWA update lifecycle remain functional.
9. A campaign-economy simulation demonstrates the Daily reward does not materially reintroduce coin inflation.

## Explicitly deferred

- Cloud accounts/sync
- Global leaderboards
- Server-authoritative anti-cheat/time
- Social/friend challenges
- Runtime AI puzzle generation
- New production corpus or campaign mutation
- Monetization/energy systems

These require separate product/security/privacy decisions and are not necessary for V1.3.

## Implementation order

1. Daily policy + deterministic selector tests.
2. Daily durable record + migration/save contracts.
3. Daily gameplay mode using existing game logic.
4. Atomic completion/reward + economy simulation.
5. Daily streak derivation + stats/milestones.
6. Compact Daily UI.
7. Chromium/WebKit/offline/migration regression.

## Definition of Done

V1.3 is complete when a player can open the PWA offline, enter today's deterministic challenge, complete it using the existing gameplay engine, receive at most one verified daily reward, retain/recover the result across reload/export/import, see daily streak/stats, and continue normal campaign gameplay with no V1.2 regression or protected-content change.
